# 口径是怎么定下来的：四要素、四层锁定、一份指标字典

> 配套：`S1_设计思路.md`（流程与判断）、`项目框架.md`、`sql/`
> 这份文档回答一个问题：**每一层的数据口径，依据什么确定？**

---

## 一、先把"口径"拆开：一个完整口径必须回答四个问题

很多人说"口径"的时候，其实只想到了公式。但公式只占四分之一。**缺任何一个要素，两个人算出来的数就不一样。**

| 要素 | 它回答的问题 | 本项目的例子 |
|---|---|---|
| **① 范围** | 谁算进来？ | GMV 只看 `delivered`；延迟率只看已送达订单 |
| **② 粒度** | 一行代表什么？ | `dwd_orders` 一行 = 1 订单；`dwd_order_items` 一行 = 1 订单商品 |
| **③ 时间** | 算在哪一天 / 哪一月？ | 一律按**下单时间**归属，不是签收时间 |
| **④ 公式** | 用哪些字段、怎么算？ | `SUM(price + freight_value)`，不是 `SUM(payment_value)` |

**这四要素就是口径的检查清单。** 以后跟业务方对齐、跟同事交接、追问，都按这四个问回去，一个都别漏。

---

## 二、口径不是"规定"出来的，是倒推出来的

我不会凭空定一个口径，而是问三个问题：

**问题 1：这个数字给谁看？他拿它做什么决策？**
> 如果是给运营看"履约体验"，那"延迟"必须用**客户感知的签收时间**，而不是仓库发货时间——因为客户投诉的是"我等了多久"，不是"你仓库里压了多久"。
> **口径由决策倒推，不由数据可得性倒推。**

**问题 2：同一个口径会被几张表、几个人用到？**
> 用得多 → 必须下沉到 dws，定义一次、全局引用；
> 只用一次 → 留在那一张 ads 表里就够了，不要过度抽象。

**问题 3：这个口径会不会变？**
> 会变 → 集中放一处，方便以后改（比如"GMV 是否含运费"这类随时可能被业务推翻的口径）；
> 不会变 → 就地写，不必抽象。

## 三、每一层锁定口径的哪一部分（这是核心）

分层不是为了分层。**分层的真正目的，是让口径各有归属：不重复定义、不互相矛盾、不互相污染。**

| 层 | 锁定什么口径 | 一句话理由 |
|---|---|---|
| **ods** | **不锁定任何口径** | 保住"能回到任何口径"的能力 |
| **dwd** | **语义口径**：粒度、字段含义、空值语义 | 这些是客观的，与业务立场无关 |
| **dws** | **业务口径**：GMV、延迟率、客户、时间归属 | 带立场、会被反复引用，必须唯一定义 |
| **ads** | **呈现口径**：对照口径、排序键、地图用名 | 只服务于"看得懂"，不新增定义 |

### ods 层：口径是"不做决定"

这一条最反直觉。**ods 层的"口径"就是"没有口径"**——全量、全 VARCHAR、不加约束、不去重。

为什么？因为 ods 的职责是"**能回到任何口径**"。如果导入阶段就固化"只保留 delivered 订单"，ods 就从"数据源"变成了"带立场的中间结果"，业务一旦要换口径，你得重新导一遍数据。

> **判断依据**：这件事是不是客观的、任何分析都成立的？
> 是 → 可以下沉。不是 → 留到有立场的那一层再决定。

### dwd 层：锁定"语义口径"（客观，无立场）

dwd 回答的是"**数据对不对**"，所以它锁定的口径全部是**与业务立场无关的客观事实**：

1. **粒度**：一行代表什么（这是表的主键，定错下游全错）
2. **字段类型与含义**：`order_amount` 到底等于什么
3. **空值语义**：`NULL` = 未知，`'unknown'` = 缺失的品类，`0` = 真的零
4. **派生字段的严格定义**：`is_late` 是 `{1, 0, NULL}` 三态，`NULL` 专门表示"未送达，无法判断"

**dwd 层最关键的一条纪律：不做任何业务筛选。**

不删取消订单、不删异常值、不删缺失行。因为"哪些数据该排除"是**分析问题**，不同的分析答案不同——它属于更上面的层。dwd 只负责如实描述，不负责站队。

### dws 层：锁定"业务口径"（带立场，唯一定义）

dws 回答的是"**算得贵不贵**"——把会反复复用的指标一次算好。所以这里是**全项目口径的唯一出处**：

1. **GMV** = `SUM(order_amount)`，且仅 `is_delivered = 1`
2. **延迟率** = `AVG(is_late)`，分母自动排除 `NULL`
3. **客户** = `customer_unique_id`（绝不是 `customer_id`）
4. **时间归属** = 一律按 `purchase_ts`（下单时间）
5. **复购** = `order_cnt > 1`
6. **留存** = 首购月为 cohort，基准日 = 最后下单日 + 1 天
7. **RFM 基准日** = `@base_date`（可复现时应硬编码）

**纪律**：ads 层和 Python 脚本**只能引用**这里的口径，不允许各自重新定义。一旦某一层自己算了一个"GMV"，这个项目就开始出现两个真相。

**关于"时间归属为什么统一按下单时间"**：如果 GMV 按签收日、留存按下单日，客户的"首购月"和"GMV 归属月"就会错配，同期群分析直接失效。统一按下单时间是电商行业惯例。
但它有一个副作用必须知道：**近一个月的订单还没送达，GMV 会被低估**。所以我保留 `gmv_all` 作为对照——这样画趋势图时能一眼区分"真实下滑"和"口径造成的假性下跌"。

### ads 层：锁定"呈现口径"（只做适配，不改定义）

ads 回答的是"**别人看不看得懂**"，它只做两件事：

1. **把容易混淆的口径显式化**：`gmv` 与 `gmv_all` 并列，让人自己对照；
2. **补呈现需要但不参与分析的附件**：`bucket_order`（分档排序键）、`state_name`（Tableau 地图用名）、`region`（大区下钻维度）。

**一条铁律：ads 层不允许出现任何新的口径定义。**
如果 Tableau 里算出了一个 SQL 里没有的数，那就是**口径泄漏**——而且它藏在一个你永远不会 review 的地方。

## 四、口径下沉规则：怎么判断该放哪一层

| 口径要素 | 锁定层 | 判断依据 |
|---|---|---|
| 字段类型、空值语义 | **dwd** | 客观、与立场无关，且每个下游都要用 |
| 粒度（一行 = 什么） | **dwd** | 它是表的主键，一旦定错下游全错 |
| 业务过滤（谁算进来） | **dws** | 这是"立场"，会随分析目的变，必须显式 |
| 指标公式 | **dws** | 会被反复引用，必须定义一次 |
| 时间归属 | **dws** | 影响所有时间序列的一致性 |
| 呈现辅助（对照口径、排序键） | **ads** | 只服务于"看得懂" |
| 数据排除规则（剔异常值） | **不在数仓层** | 属于具体分析，由 Python 按分析目的决定并写进报告 |

**抽象成一句话**：

> **口径的下沉深度 = 复用范围 × 稳定性**
> 复用广且稳定 → 沉到 dws；复用窄且易变 → 留在当层。

**还有一条实用技巧：把口径写进字段名。**
`gmv` 和 `gmv_all` 而不是两个都叫 `gmv`；`is_late` 而不是 `late`。
**命名本身就是最便宜的口径文档**——没人会去看注释，但所有人都会看字段名。

## 五、口径最容易出错的 5 个地方

| # | 错误 | 症状 | 正确做法 |
|---|---|---|---|
| 1 | **时间归属偷换** | GMV 用签收日算，近月"看起来正常"（因为未送达的订单根本没进来） | 全局统一按下单日，并用 `gmv_all` 对照 |
| 2 | **分母偷换** | 延迟率的分母用了"全部订单"，未送达订单被默认算作"没延迟"，延迟率被系统性低估 | 分母必须是"已送达且承诺时间已知"的订单，用 `NULL` 自动排除 |
| 3 | **粒度偷换** | 品类维度用了订单级金额 `order_amount`，一单含 3 个品类就被重复计 3 次 | 品类/卖家维度必须用**明细金额** `price + freight_value` |
| 4 | **空值被当成 0** | `is_late` 用 0 表示未送达，等于把"不知道"当成"准时" | 三态：`1` 延迟 / `0` 准时 / `NULL` 未知 |
| 5 | **JOIN 后重复计数** | 维表 join 后行数膨胀，`SUM` 翻倍（详见 `S1_设计思路.md` 第六节） | JOIN 前先对齐粒度 |

第 4 条尤其隐蔽。**"不知道"和"否"必须分开**——这是统计学的基本功，但落到数仓里就变成了一个 `0` 和 `NULL` 的区别。

## 六、怎么验证口径是对的

定了不等于对。三招，缺一不可：

**第一招：勾稽校验（内部自洽）**
```
item_amount + freight_amount − order_amount ≡ 0
```
这条恒等式必须严格成立。它验证的是"我自己的字段之间没有相互矛盾"。

**第二招：多路径对账（外部一致）**
同一个数，用 SQL 算一遍，再用 Excel 独立算一遍，必须一致。
数字必须能被**独立复算**，不能只有"我这条 SQL 能算出来"。

**第三招：量纲直觉检查（sanity check）**
在算之前，先知道答案大概长什么样：
- 延迟率应该在**个位数百分比**；
- 平均评分应该在 **4 分左右**（电商平台的常见水平）；
- 复购率在 marketplace 上应该是**极低**的。

如果跑出个"延迟率 40%"或"平均评分 2.1"，**先怀疑口径，再怀疑业务**。
这一步看着不严谨，但它是真能救命的一步——**先猜答案，再看结果**。

## 七、本项目口径清单（逐层）

### ods 层（0 条）
不定义任何口径：全量、全 `VARCHAR`、不加主键约束、不去重。

### dwd 层（7 条语义口径）
1. 粒度：`dwd_orders` = 1 行/订单；`dwd_order_items` = 1 行/订单商品
2. 空值语义：`NULL` = 未知；`'unknown'` = 缺失品类；`0` = 真的零
3. `is_late` ∈ {1, 0, NULL}，`NULL` = 未送达，不参与延迟率分母
4. `order_amount = item_amount + freight_amount`（运费计入订单总额）
5. 时间统一转 `DATETIME`；时长统一用**小时**（`INT`），避免天数小数丢精度
6. 维表一律 LEFT JOIN，缺失保留 `NULL`，**不丢行**
7. 异常值（如签收早于审批）**只标记不删除**

### dws 层（7 条业务口径）
1. **GMV** = `SUM(order_amount)`，仅 `is_delivered = 1`
2. **延迟率** = `AVG(is_late)`，分母自动排除 `NULL`
3. **客户** = `customer_unique_id`
4. **时间归属** = 按下单时间 `purchase_ts`
5. **复购** = 订单数 > 1
6. **留存** = 首购月为同期群，基准日 = 最后下单日 + 1 天
7. **RFM 基准日** = `@base_date`（要可复现就硬编码）

### ads 层（4 条呈现口径）
1. 保留 `gmv` / `gmv_all` 双口径对照
2. 延迟分档边界：准时或提前 / 1-3 天 / 4-7 天 / 8-14 天 / 15 天以上，并配 `bucket_order` 排序键
3. 州名用带重音正规写法（`São Paulo` / `Amapá`）+ 五大区
4. **不新增任何计算口径**

## 八、指标字典（可直接作为 S1 交付物）

| 指标 | 所在表 | 口径定义 | 计算表达式 | 注意事项 |
|---|---|---|---|---|
| GMV（已送达） | `dws_daily_gmv`、`ads_kpi_overview` | 仅 delivered，含运费 | `SUM(CASE WHEN is_delivered=1 THEN order_amount ELSE 0 END)` | 近月偏低，需对照 gmv_all |
| GMV（全口径） | 同上 | 全部订单状态 | `SUM(order_amount)` | 仅做对照，不作为考核口径 |
| 订单数 | 同上 | 全部状态 | `COUNT(*)` | — |
| 已送达订单数 | 同上 | `is_delivered=1` | `SUM(is_delivered)` | 客单价的分母 |
| 下单客户数 | 同上 | 去重客户 | `COUNT(DISTINCT customer_unique_id)` | **不能用 customer_id** |
| 商品件数 | 同上 | 订单明细行数 | `SUM(item_cnt)` | 1 行明细 = 1 件 |
| 客单价 AOV | 同上 | GMV / 已送达订单数 | `gmv / delivered_cnt` | 分母是订单不是客户 |
| 人均消费 ARPU | 同上 | GMV / 下单客户数 | `gmv / buyer_cnt` | 分母是客户 |
| 件均价 | `dws_category_monthly` | 商品金额 / 件数 | `SUM(item_amount)/SUM(item_cnt)` | 不含运费 |
| 运费占比 | 同上 | 运费 / GMV | `SUM(freight_amount)/SUM(gmv)` | 用 delivered 口径 |
| 履约总时长 | `dwd_orders` | 下单 → 签收 | `TIMESTAMPDIFF(HOUR, purchase_ts, customer_delivered_ts)` | 单位小时 |
| 履约三段时长 | `dwd_orders` | 审批 / 交承运商 / 末端配送 | `approve_hours`、`carrier_hours`、`lastmile_hours` | 用于定位卡在哪一段 |
| 是否延迟 `is_late` | `dwd_orders` | 签收 > 承诺送达 | 三态 1 / 0 / NULL | NULL 不参与分母 |
| 延迟率 | `dws_daily_gmv`、`ads_state_delivery` | 延迟订单 / 已送达订单 | `AVG(is_late)` | 分母自动排除 NULL |
| 平均评分 | `dws_daily_gmv` | 同一订单多条评价取均值 | `AVG(review_score)` | 先聚合到订单粒度 |
| 差评率 | `dws_category_monthly` | 评分 ≤ 2 | `AVG(review_score<=2)` | 空评分不计入分母 |
| 一星率 | `ads_delivery_delay_impact` | 评分 = 1 | `AVG(review_score=1)` | 最能反映极端不满 |
| 复购客户 | `dws_user_profile` | 订单数 > 1 | `order_cnt > 1` | Olist 仅约 3% |
| 复购率 | `dws_user_profile` | 复购客户 / 全部客户 | `AVG(is_repeat)` | 分母是客户不是订单 |
| R / F / M 分 | `dws_user_profile` | 五分位打分 | `NTILE(5)`；**R 反向**（recency 越小分越高） | 二级排序加唯一键保证可复现 |
| RFM 人群 | `dws_user_profile` | R/F/M 是否 ≥ 4 划八类 | `CASE WHEN ...` | 阈值 4 是"高于平均"的意思 |
| 留存率（第 N 月） | `dws_cohort_retention` | 同期群第 N 月活跃 / 同期群人数 | `active_users / cohort_size` | 复购率低，第 1 月起会断崖 |
| 卖家 ABC | `ads_seller_scorecard` | GMV 降序累积占比 | `<=80% A`、`<=95% B`、其余 C | 累积窗口 ORDER BY 要带唯一列 |
| 品类四象限 | `ads_category_matrix` | GMV vs 平均 GMV；增长率 vs 0 | 明星 / 现金牛 / 潜力 / 观察汰换 | 增长口径 = 近 3 月 vs 前 3 月 |
| 买卖家距离 | `dwd_order_items` | Haversine **直线距离** | `6371 * ACOS(...)` | **≠ 实际运输距离**，只作代理变量 |
