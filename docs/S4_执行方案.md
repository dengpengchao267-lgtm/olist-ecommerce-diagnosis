# S4 执行方案：差评预警（签收后、评价前）

> 定位：S3 证明了"延迟与低分的关联"，S4 把它升级成**可运营的预警能力**——
> 在客户写下差评之前认出高风险订单，主动干预。这是全项目最能体现
> "分析 → 模型 → 业务动作 → 钱"闭环的一个专题。

## 一、业务设定

| 要素 | 设定 |
|---|---|
| 预警时点 | 订单**签收后、评价前**（此点履约特征全部已知，评价尚未发生） |
| 预测目标 | 该订单将收到差评（`review_score ≤ 2`，1~2 星；3 星为中性不进正类） |
| 干预动作 | 头部风险单主动关怀 + 优惠券（成本假设 R$15/单，config 可调） |
| 业务价值 | 拦截差评 = 保住评分体系健康度（前端展示、卖家考核、转化率） |

## 二、执行顺序

```
1. sql/09_s4_差评预警特征.sql     -- 建特征宽表 + 4 条自检（3.3 防泄漏检查必看）
2. python s4_01_bad_review_model.py --dry-run   -- 先看数
3. python s4_01_bad_review_model.py             -- 回写 3 张表
```

前置依赖：仅 S1（dwd 层）。S3 结果不阻塞 S4（特征各自独立计算），但 S3 的结论
（延迟与评分的关联强度）是 S4 的**业务叙事起点**：先有"延迟伤分"的诊断，才有"预警干预"的动作。

## 四、模型与评估的四个关键选择（答案都在脚本注释里）

| 选择 | 理由 |
|---|---|
| 时间外推划分，不做随机 split | 随机切分让模型"偷看未来"，指标虚高；上线面对的永远是"用历史预测未来" |
| 主指标 PR-AUC，不用准确率/ROC-AUC | ~10% 不平衡类：全预测好评就有 90% 准确率；ROC-AUC 在不平衡下虚高 |
| 阈值取训练集 F1 最大点，不用 0.5 | 阈值对应干预预算，不是概率语义；测试集只看一次 |
| 逻辑回归 + 梯度提升树双模型 | 白盒可解释 vs 性能上限；两模型差距本身是诊断信息 |

划分：train 2017-01 ~ 2018-04（16 个月），test 2018-05 ~ 2018-08（4 个月）。

## 五、产出表清单（4 张）

| 表 | 粒度 | 谁写的 | 用途 |
|---|---|---|---|
| `ads_s4_order_features` | 订单 | sql/09 | 特征宽表 + 标签（训练与预测同源） |
| `ads_s4_eval` | 模型×指标 | s4_01 | PR-AUC / ROC-AUC / Brier / 阈值下 P&R |
| `ads_s4_gain` | 模型×头部比例 | s4_01 | **干预增益曲线**（拦前 k% 覆盖多少差评 + 每单成本） |
| `ads_s4_importance` | 模型×特征 | s4_01 | logreg 标准化系数 / hgb 置换重要性 |

## 六、怎么读结果（跑完看什么）

1. **PR-AUC**：0.5 左右=模型接近没用了；0.3+（基线=差评率≈0.1 时 PR-AUC=0.1）即有信号；
   0.4+ 是不错的水平（本数据集 Kaggle 参考多在 0.35~0.45）。
2. **增益曲线默认汇报口径 = 拦前 10%**：覆盖差评比例（recall）× 精度（lift）
   × 每拦一单成本（R$）——这一行就是给业务方的"报价单"。
3. **两模型差距**：hgb 明显高于 logreg ⇒ 存在非线性/交互（大概率是
   延迟×品类、历史差评率×金额的交互）；差距小 ⇒ 线性故事就够讲。
4. **特征重要性**：`seller_hist_bad_rate` 和 `delay_hours` 谁排第一，
   决定干预故事是"卖家治理"还是"物流提速"——直接影响 S6 的策略建议。
