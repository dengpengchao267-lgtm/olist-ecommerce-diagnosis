# S3 执行方案：履约体验分析

> 定位：S2 回答了"GMV 涨在哪"，S3 回答"履约体验伤在哪、值多少钱"。
> 产出直接对接 S4 差评预警（延迟是差评最强候选特征）与增长策略（时效是可运营杠杆）。

## 一、回答的三个业务问题

| # | 问题 | 对应脚本 | 产出表 |
|---|---|---|---|
| Q1 | 延迟送达真的伤评分吗？伤多少？越晚越重吗？ | s3_01 | `ads_s3_score_diff` / `ads_s3_delay_impact` |
| Q2 | 延迟集中在哪：哪些品类、哪些州？ | s3_02 | `ads_s3_bottleneck` |
| Q3 | 链路哪一环最慢？延迟单的时间丢在哪个环节？延迟率整体在改善还是恶化？ | s3_02 | `ads_s3_stage` + 月度表 MK 检验 |

## 二、口径（继承 + 新增）

**继承 S2**：时间归属 = `purchase_ts`；分析窗口 = 完整月窗口（2017-01 ~ 2018-08）；GMV 仅 `is_delivered=1`。

**S3 新增**：

1. **履约口径订单** = 已送达 且 签收时间/承诺送达时间齐全（即 `is_late IS NOT NULL`）
2. **延迟** = 签收 > 承诺（严格大于）；`delay_hours` 带符号
3. **卖家违约** = 交承运商时间 > 订单内最早 `shipping_limit_ts`
4. **延迟分桶**（7 桶，小时边界，左开右闭）：提前>10天 / 提前3~10天 / 准时≤3天（对照组）/ 延迟0~3 / 3~7 / 7~14 / >14天
   —— ⚠️ 边界同时写在 `sql/08` 和 `s3_01.py` 的 `BUCKETS`，改一处必须同步另一处
5. **品类粒度声明**：一个订单含多品类时，在每个所含品类下各计 1 次（订单×品类去重）；GMV 按明细行拆分，跨品类加总不重复。各品类订单数之和 > 总订单数，报告必须写明

**⚠️ 右端截断（S3 特有，报告必写）**：最近月份有"已下单未送达"的订单，它们不进履约口径 → 近期延迟率被**低估**。
处理：`ads_s3_fulfillment_monthly.delivered_ratio` 做诊断，低于 `S3_TRUNCATION_RATIO=0.90` 的月份从趋势检验剔除（不删数据，只影响 MK 检验样本）。

## 四、执行顺序

```
1. sql/08_s3_履约链路.sql     -- 建表 + 汇总 + 4 条勾稽自检（必须全过再往下）
2. python s3_01_delay_impact.py --dry-run   -- 先看数对不对
3. python s3_01_delay_impact.py             -- 回写 2 张表
4. python s3_02_bottleneck.py --dry-run
5. python s3_02_bottleneck.py              -- 回写 2 张表
```

`selftest.py` 不受影响（S3 未改任何 S1/S2 代码，仅 config.py 追加参数）。
Tableau 看板等 S4~S6 分析全部跑完统一做（邓的要求）。
