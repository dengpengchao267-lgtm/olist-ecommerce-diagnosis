# 技术栈分工与工具边界

> 配套文档：`../项目框架.md` ｜ 技术栈：MySQL · Python · Tableau

---

## 一、三条总原则

1. **MySQL 是唯一数据源**（single source of truth）——所有指标口径沉淀在这里；
2. **Python 只做 MySQL 做不了的事**——统计推断与机器学习，算完把结果**写回** MySQL；
3. **Tableau 只做呈现**——直连 ads 层结果表，不碰原始表。

**判断口诀**：能算在数据库里的，不要拉到内存里；能用 SQL 表达的，不要用 Python 写循环；能在 SQL 里出的结果，不要藏在报表的计算字段里。

## 二、三大软件的总分工

| 软件 | 在项目里的角色 | 具体负责 | 明确不做 | 判断依据 |
|---|---|---|---|---|
| **MySQL 8.0** | 数据仓库与指标计算引擎 | 9 张表导入、四层建仓（ods / dwd / dws / ads）、多表 join、窗口函数、CTE、日期函数、指标口径定义与落表、索引与 `EXPLAIN` 优化 | 统计推断、机器学习、画图 | 数据量大、要反复复用、口径必须统一 |
| **Python 3** | 统计推断与建模工作台 | 缺失值处理与特征工程、假设检验、回归、聚类、生存分析、因果推断、模型评估、结果回写 MySQL | 存原始数据、做业务交付图、代替 SQL 做聚合 | 需要 p 值 / 置信区间 / 模型 / 分布假设 |
| **Tableau** | 可视化与交互交付层 | 4 页看板、KPI 卡、趋势图、瀑布图、地图、散点、参数切换、仪表盘动作下钻、发布 Tableau Public | 复杂计算、数据清洗、连接原始表 | 目的只是"让人看懂并做决策" |

## 四、Python 内部各库的分工

| 库 | 负责什么 | 在本项目哪里用 |
|---|---|---|
| `pandas` / `numpy` | 数据读写、变形、聚合、向量化 | 所有脚本的进出口 |
| `sqlalchemy` / `pymysql` | 与 MySQL 的读写通道 | 所有脚本的数据库连接 |
| `scipy.stats` | 假设检验、概率分布、Bootstrap | S6：t 检验、卡方 SRM 检验、功效计算 |
| `statsmodels` | 回归与统计模型（带完整统计输出：系数、标准误、p 值） | S3 分位数回归、S4 逻辑回归、S6 DID |
| `scikit-learn` | 机器学习、聚类、模型评估 | S4 随机森林、S5 K-means 与轮廓系数 |
| `lifelines` | 生存分析 | S5 Kaplan-Meier、Cox 回归 |
| `shap` | 模型可解释性 | S4 特征归因 |
| `matplotlib` / `seaborn` | **探索性**绘图（给自己看的） | 开发期看分布、相关性、散点 |
| `missingno` | 缺失值可视化体检 | S1 数据体检 |
| `jupyter` | 交互式探索草稿 | 开发期使用；最终逻辑必须固化成 `.py` |

## 五、周边工具的分工

| 工具 | 用途 | 边界 |
|---|---|---|
|  datagrip | MySQL 客户端：导入 CSV、跑 SQL、看表结构 | 只做交互式调试，正式脚本必须落地成 `.sql` 文件 |
| PyCharm | 写 `.py` 与 `.sql` 脚本 | — |
| Jupyter | 探索性分析草稿 | 草稿不进仓库 |
| Git + GitHub | 版本管理与作品展示 | 数据文件 `.gitignore`，不进仓库 |
| Tableau Public | 看板发布 | 链接直接写进 |
| Excel | 快速核对数字（用 SUMIFS 验证 SQL 口径对不对） | **只做校验，不做交付** |
| Kaggle | 公开数据集下载 | — |

Excel 这个位置要特别说明：它是**交叉验证工具**，不是交付工具。用 Excel 独立算一遍月度 GMV，和 SQL 的结果对不上，说明你的 SQL 口径写错了——这是很实用的自检手段，也可以讲。
