# S2 执行方案：GMV 拆解与增长归因

> S1 已经建好了地基（9 张 ods + 6 张 dwd + 口径字典）。S2 是**第一次真正产出业务结论**的阶段——
> 前面所有工作都是为了这一步能说出一句可信的话。

---

## 零、一句话验收标准

S2 做完，你必须能流利说出这样一句话：

> **「GMV 从 100 万降到 92 万，−8%。其中『下单人数』贡献 −6.4pp（占八成）、『客单价』贡献 −1.2pp、『人均频次』贡献 −0.4pp。主因是 A 品类在东南部两个州的下滑。建议动作是 X，按当前客单价估算年化增量约 ¥Y 万。」**

三个数字**相加必须严格等于总变化**——这是这一阶段的硬性勾稽要求，也是唯一能立刻验证你的地方。

## 二、拆解骨架：从 GMV 拆到可执行动作

**四个步骤，不能跳、不能换顺序：**

| 步骤 | 回答的问题 | 方法 | 产出 |
|---|---|---|---|
| **① 找拐点** | 什么时候开始变的？ | 环比/同比 + 移动平均 + 趋势检验 | 拐点月份 |
| **② 找主因** | 是量的问题还是价的问题？ | **三因子分解 + 贡献度分解** | 三个因子的贡献占比 |
| **③ 找战场** | 具体是哪些品类/州？ | 结构下钻 + mix 效应 | Top 贡献/拖累维度 |
| **④ 讲价值** | 该做什么，值多少钱？ | 动作 → 客单价 × 影响面 → 增量 | 一句结论 + 一个数 |

跳过①②直接下钻（很多人这么干）会得到一个"很多品类都在跌"的无结论报告；跳过④则整个项目变成学术练习。

## 三、拆解公式：三层，每层都可勾稽

```
L0（总量）    GMV
                 │
L1（三因子）   GMV = 下单客户数 × 人均下单次数 × 客单价
                 │        buyers      orders_per_buyer   aov
L2（结构）     每个因子 → 品类 / 州 / 月份
```

用**乘法链**而不是加法链，原因只有一个：**三个因子相乘能还原 GMV，可以做勾稽校验**。如果拆成"新客 GMV + 老客 GMV"，你只能验证加总，验证不了口径。

> ⚠️ **口径必须先钉死（S1 已定，S2 直接引用，不再重新讨论）**
> - `GMV = Σ(item_amount + freight_amount)`，**仅 `is_delivered = 1`**（含运费）
> - 时间归属 = **`purchase_ts`（下单时间）**，不是签收时间
> - 用户 = **`customer_unique_id`**（不是 `customer_id`）
> - 客单价 `aov = GMV / 已送达订单数`

## 四、三个方法，缺一不可

### 4.1 环比 / 同比 —— 找「什么时候变的」

- **环比**：看短期波动。Olist 数据里有明显的 11 月黑五尖峰，环比会被它干扰。
- **同比**：只有 2017 和 2018 有可比月份，**且 2017 上半年不完整**，所以同比只在少数月份可用。
- 加一条 **3 个月移动平均**，把噪音压掉再判断趋势。

### 4.2 贡献度分解 —— 找「是谁变的」★ 核心

**朴素加法分解（Laspeyres 型）**：

```
ΔGMV = ΔQ × P₀  +  Q₀ × ΔP  +  ΔQ × ΔP
        └量效应┘   └价效应┘   └交叉项┘
```

问题：**交叉项该算给谁？** 没有客观答案，人为指定会让结论随你怎么分而变——一定会问这个。

**对数分解（LMDI，对数平均迪氏指数法）**：

```
              L(GMV₁, GMV₀)          GMV₁ − GMV₀
ΔGMV_因子ᵢ = ───────────────── × ln(─────────────)
                  GMV₁ − GMV₀          ln(GMV₁) − ln(GMV₀)
```

LMDI 的三个性质正好解决上面的问题：**无残差（三项相加严格等于 ΔGMV）、可加、因子对称**。所以选它。

**必做勾稽**：

```python
assert abs(contrib_buyers + contrib_opb + contrib_aov - delta_gmv) < 0.01
```

这一行断言就是 S2 的验收开关。

### 4.3 Bootstrap 置信区间 —— 找「这个变化是噪音还是真的」

前两步告诉你"变了多少"，但**没说这个变化是不是随机波动**。

做法：对样本（按天或按订单）有放回重抽样 1000 次，重算三因子贡献，取 2.5% / 97.5% 分位得到置信区间。

- 区间**不跨越 0** → 这个因子确实在起作用，可以拿去汇报
- 区间**跨越 0** → 只能说"未观察到显著影响"，不能说"没有影响"

> **这是你相对于计算机背景候选人最大的一处差异化。** 别人交付的是"环比 −8%"，你交付的是"−8%，95% CI [−11%, −5%]，显著"。一句话分层。

## 五、Olist 数据上，这一步会出现一个很重要的结论

因为**平台复购率只有约 3%**，`orders_per_buyer` 会长期贴在 **1.0X** 附近几乎不动。这意味着：

> **三因子分解的结果大概率是：GMV 的涨跌几乎 100% 由「下单人数」一个因子解释，人均频次与客单价的贡献接近于零。**

这不是数据没分析好，**这本身就是一个强业务结论**：

- 平台的增长模型是**纯拉新模式**，复购几乎没有贡献
- 客单价也不是杠杆（品类结构稳定，没有升级路径）
- ⇒ **最大的未开发杠杆是复购**，而不是"再拉更多新客"

这个结论会自然地把报告引向 S5 的复购专题，整份报告就有了**一条主线**，而不是六个互不相干的专题拼盘。

> 这句话很值钱：**"我先用三因子分解证明了这个平台的增长完全是拉新驱动，复购贡献不到 3%，所以后续所有建议都围绕复购展开。"** ——这叫"用数据决定分析方向"，而不是"我做了六个分析"。

### 需要补的两张（写在 S2 脚本里）

**① `dws_state_monthly`** —— 月 × 州。因为 `ads_gmv_factors` 只到总量层，结构下钻需要州维度。

```sql
CREATE TABLE dws_state_monthly (
  stat_month DATE NOT NULL,
  customer_state CHAR(2) NOT NULL,
  order_cnt INT, buyer_cnt INT, item_cnt INT,
  gmv DECIMAL(14,2), aov DECIMAL(10,2),
  avg_review_score DECIMAL(4,2), late_rate DECIMAL(6,4),
  PRIMARY KEY (stat_month, customer_state)
);
```
（品类维度直接复用 `dws_category_monthly`，不重复建。）

**② `ads_gmv_structure`** —— 结构与贡献度结果表（Python 回写）。

```sql
CREATE TABLE ads_gmv_structure (
  stat_month DATE NOT NULL,
  dim_type VARCHAR(10) NOT NULL,   -- 'category' / 'state'
  dim_value VARCHAR(100) NOT NULL,
  gmv DECIMAL(14,2),
  gmv_prev DECIMAL(14,2),
  gmv_share DECIMAL(8,4),          -- 本期份额
  growth_pct DECIMAL(8,2),         -- 本维度自身增长率
  contrib_pp DECIMAL(8,4),         -- 对整体环比增长的贡献（百分点）
  is_significant TINYINT,          -- Bootstrap 判定
  PRIMARY KEY (stat_month, dim_type, dim_value)
);
```

### S2 开工第一条 SQL：先看清数据长什么样

```sql
SELECT DATE_FORMAT(purchase_ts, '%Y-%m') AS ym,
       COUNT(*) AS order_cnt,
       SUM(is_delivered) AS delivered_cnt,
       ROUND(SUM(CASE WHEN is_delivered = 1 THEN order_amount ELSE 0 END), 2) AS gmv
FROM dwd_orders
WHERE purchase_ts IS NOT NULL
GROUP BY 1 ORDER BY 1;
```

**这一步必须先做，它会暴露 S2 最大的坑（见第八节）。**

| 脚本 | 做什么 | 回写目标 |

**两个方法论细节（会问）**：

1. **Bootstrap 该按什么重抽样？**
   按订单重抽样会忽略时间结构，按天重抽样更贴近"月度 GMV 是若干天之和"这一事实。**推荐按天**，并在文档里说明原因——这个选择本身就是加分项。
2. **为什么用 Mann-Kendall 而不是简单看斜率？**
   Mann-Kendall 是**非参数**检验，不要求正态、对异常值稳健。GMV 月度序列有明显的季节尖峰，用 OLS 斜率会被 11 月黑五带偏。

## 八、三个必须提前处理的数据坑

### 坑 1（最致命）：首尾月份不完整，趋势是假的

Olist 数据在 **2016-09 之前几乎没有数据，2018-09 之后订单量骤降到个位数**（2018-10 之后干脆没有）。如果直接按月画趋势：

- 起点会是一个"暴涨"的假象
- 终点会是一个"断崖"的假象

**处理**：只保留**完整月**（订单量达到平台月均一定比例的月份），把首尾剔除，并在报告里写明"分析区间 XXXX-XX ~ XXXX-XX，剔除首尾不完整月"。**排除规则要写进口径文档**——这本身就是"我怎么保证结论可信"的答案。

### 坑 2：同比基本不可用

2017 上半年数据不完整，所以"2018 年 5 月 vs 2017 年 5 月"这种对比大部分做不了。**S2 主力用环比 + 移动平均，同比只在可用月份做补充。**

### 坑 3：复购率约 3%，别过度解读人均频次

`orders_per_buyer` 会长期贴在 1.0X——它是**结构常数，不是业务变量**。报告里要把它当"证明平台是拉新模式"的证据，而不是当"今年频次下降了 0.3%"来解读（那是噪音）。
