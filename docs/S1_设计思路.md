# S1 设计思路（数据底座与指标体系）

> 配套文件：`项目框架.md`、`sql/`（00–04）、`docs/技术栈分工说明.md`
> 这份文档记录的是 **"为什么这么写"**，不是"写了什么"。能讲出来的就是这一层。

---

## 一、先想清楚：S1 到底在干什么

大部分人把 S1 理解成"把 CSV 导进数据库"。如果这么理解，这一步就白做了。

**S1 真正的目标**：把一堆原始文件，变成**口径统一、可信、可复用的分析底座**。

验收标准我定成一句可检验的话：

> 打开数据库，一条 SQL 就能跑出任意一天的 GMV，且这个数字能被 Excel 独立复算出来。

注意这句话里有两个约束：
- **"一条 SQL 就能跑出"** → 说明口径已经沉淀到数据库里了，不是每个人自己写一套；
- **"能被 Excel 复算"** → 说明这个数字是可验证的，不是"我觉得对"。

这两个约束倒过来决定了后面所有的设计选择。

---

## 二、思考顺序：六步，不能跳

```
体检 → 定口径 → 分层 → 清洗 → 汇总 → 校验
（了解数据）（定规则）（定结构）（做加工）（做复用）（做对账）
```

**最关键的是顺序**。最容易犯的错是拿到数据就开始写 CREATE TABLE——那样写出来的表，改三次都不够。

必须先体检、先定口径，再动手建表。因为**表结构是口径的物化**，口径没定，表结构一定是错的。

---

## 三、第一步：体检先行（产出「数据坑清单」）

写任何一行 DDL 之前，先回答 5 个问题。这 5 个问题的答案，直接变成了后面的设计约束。

| 问题 | 对 Olist 的答案 | 它带来的设计约束 |
|---|---|---|
| ① 几张表、什么粒度、主键是什么 | 9 张表；orders 是订单粒度、order_items 是明细粒度 | 决定了 dwd 必须**拆成两张事实表**（见第六节） |
| ② 哪些字段缺失、缺失多少 | 610 条商品缺品类；未送达订单缺签收时间 | 决定了"缺失兜底"策略：品类填 unknown，未送达标记 NULL 而不是 0 |
| ③ 有没有逻辑错误 | 存在"签收时间早于审批时间"的行 | 决定了**只标记不删除**（见第七节） |
| ④ 时间覆盖有没有偏 | 2016-09 只有个位数订单，2017-01 才上量 | 决定了趋势分析必须从 2017-01 起画 |
| ⑤ 有没有"看着像但其实不是"的字段 | **`customer_id` 不是客户** | 决定了所有用户级聚合必须用 `customer_unique_id` |

第 ⑤ 条是这次体检最大的收获。Olist 每下一单就新建一个 `customer_id`，真正的客户主键是 `customer_unique_id`。如果用错：
- 会得出"复购率 100%"这种一眼假的结论；
- 而它在字段层面完全合法，不会报任何错，**静默地毁掉整个分析**。

所以我在 `04_校验与对账.sql` 里专门写了一条"体检 2"，直接算 `COUNT(DISTINCT customer_id) / COUNT(DISTINCT customer_unique_id)` 的比值——比值接近 1.00 就说明用错字段了。**把坑变成一道自动化的检查题**，这是体检环节最值钱的产出。

## 四、第二步：口径先定死（三条，写进代码注释和报告首页）

口径不定，后面所有数字都会互相打架：报表和报告对不上、这周和上周对不上、你和同事对不上。

我在 `02_dws_主题汇总.sql` 的文件头把三条口径写死：

| 口径 | 定义 | 为什么这么定 |
|---|---|---|
| **GMV** | `SUM(order_amount)`，且**仅统计 `order_status='delivered'`**，`order_amount` = 商品金额 + 运费 | 含运费是消费者实付视角；只算已送达是避免"未成交订单虚增 GMV" |
| **延迟** | 客户签收时间 > 承诺送达时间 | 这是消费者真正感知的延迟，不是"发货慢" |
| **客户** | `customer_unique_id` | 见上 |

这里有两个刻意做的处理：

**（1）延迟的"未送达"要留 NULL，不能填 0。**

未送达的订单 `is_late` 我设成 `NULL` 而不是 `0`。因为填 0 会把它们算进"准时"的分子分母，**虚低延迟率**。填 NULL 后，`AVG(is_late)` 自动只在"已送达且承诺时间已知"的订单上求平均——这是正确的分母。

> 一个细节：口径的正确性，常常体现在**你怎么处理缺失值**，而不是你怎么写公式。

**（2）GMV 同时保留两个口径供对照。**

`dws_daily_gmv` 里我同时建了 `gmv`（仅已送达）和 `gmv_all`（含全部状态）两列。

原因是"仅已送达"这个口径有个天然偏差：**最近一个月的订单还没送达，GMV 会偏低**。如果只留一个口径，画出来的趋势图末端会假性下跌，看起来像"业务崩了"。留两列对照，就能一眼区分"真实下滑"和"口径造成的低估"。

## 五、第三步：为什么分四层，以及每层的判断规则

市面上讲分层都说"ods/dwd/dws/ads"，但真正有用的是**每一层各解决一类问题**：

| 层 | 解决什么问题 | 判断规则（这张表该不该放这层） |
|---|---|---|
| **ods** | 数据从哪来、能不能回溯 | 它和源文件是不是**同一粒度、同一形态**？是 → ods |
| **dwd** | 数据对不对 | 它是不是**清洗后的最细粒度**？是 → dwd |
| **dws** | 算得贵不贵 | 它会不会被**反复复用**？会 → dws |
| **ads** | 别人看不看得懂 | 它是不是**直接给报表看的**？是 → ads |

**最关键的是 ods 层的"只搬不改"。**

ods 里 9 张表我全部用 `VARCHAR`，一个类型都不转。很多人觉得这是浪费——明明知道 price 是数字，为什么不直接建成 DECIMAL？

因为 ods 的意义是**"出错时能回溯"**。如果导入阶段就做类型转换，一旦转换失败（比如某个字段混进了空字符串），你既不知道原始值长什么样，也没法重跑。保持原始形态，等于给整个流程留了一个**可以随时重来一遍的基线**。

同理，**ods 层我不加任何主键和唯一约束**——导入后统一建索引。两个好处：
- 导入更快（索引是边插边维护的）；
- 脏数据不会导致整个导入失败（比如 `review_id` 在原始数据里其实不唯一，加主键直接报错）。

## 六、第四步：dwd 为什么拆两张事实表（最核心的技术判断）

这是整个 S1 里我最想让你记住的一点。推理过程如下：

**一个订单的真实结构是：**
```
1 条 orders 记录
  ├─ N 条 order_items
  ├─ M 条 order_payments
  └─ K 条 order_reviews
```

**如果做成一张"大宽表"，直接把三张表 JOIN 起来：**

```sql
-- 错误示范
FROM ods_orders o
JOIN ods_order_items    i ON ...
JOIN ods_order_payments p ON ...
JOIN ods_order_reviews  r ON ...
```

结果的行数是 **N × M × K**。对一笔"3 件商品 + 2 笔支付 + 1 条评价"的订单，会膨胀成 6 行。于是 `SUM(price)` 被算了 2 遍，GMV 直接翻倍。

**这个错误最阴险的地方是：它不会报错。** 你得到的数字看起来很正常，只是错了。

**正确做法——先降粒度，再合并：**

```
items    → 按 order_id 聚合 → 1 行/订单
payments → 按 order_id 聚合 → 1 行/订单
reviews  → 按 order_id 聚合 → 1 行/订单
                              ↓
                     全部 JOIN 回 orders（1 行/订单）
```

这就是我在 `01_dwd` 里用三个 CTE（`items` / `pays` / `revs`）各自聚合、再 join 回 `base` 的原因。

**拆出来的两张表：**

| 表 | 粒度 | 用途 |
|---|---|---|
| `dwd_orders` | **1 行 = 1 订单** | 订单级分析：GMV、履约时长、延迟、评分 |
| `dwd_order_items` | **1 行 = 1 订单商品** | 商品级分析：品类、卖家、价格、运费、距离 |

**这条经验的通用版本**（任何 join 场景都适用）：

> JOIN 之前先问一句：**右边的表，是不是比左边"更细"？**
> 是 → 先聚合到同粒度再 JOIN，否则行数会膨胀，聚合值会重复计算。

同一套道理我在 `02_dws` 里又用了一次：做品类月度指标时，订单级的评分/延迟率必须先 `SELECT DISTINCT (月, 品类, 订单)` 去重再求平均，否则"一单三件"会让这个订单的评分被计三次。

## 七、第五步：清洗的边界——什么在 SQL 做，什么不做

**在 SQL 做的：**
- 类型转换（VARCHAR → DATETIME / DECIMAL / INT）
- 文字清理（TRIM、大小写、补前导 0）
- 缺失兜底（品类缺失填 `unknown`）
- 派生字段（履约各段时长、延迟标记、Haversine 距离）

**刻意不在 SQL 做的：**
- 逻辑错误行**不当场删除**，只保留标记位。理由：删了就不可追溯，报告里也没法说"我剔除了 X 行异常值"。留到 Python 侧按分析目的决定要不要排除，而且要在报告里写明。
- 统计推断、模型（p 值、置信区间、聚类）——SQL 算不出来，硬凑就是错的。

**一条判断规则**：这件事需要 p 值吗？不需要 → SQL；需要 → Python。

## 九、第七步：为什么必须写校验脚本

**核心原则：不能验证的分析，等于没有分析。**

`04_校验与对账.sql` 里 13 项体检，分成四类，各有各的作用：

| 类型 | 例子 | 作用 |
|---|---|---|
| **完整性对账** | 检查 1：dwd_orders 是否 = 99,441 | 证明没丢行 |
| **口径对账** | 检查 8：GMV / 商品金额 / 运费 / 勾稽差 | 用 Excel 独立算一遍，必须一致 |
| **坑位复查** | 检查 2/3/4/5：customer_id、复购率、时间缺失、2016 数据量 | 把体检结论变成可重复执行的检查 |
| **结论预演 + 基准冻结** | 检查 9/10/13 | 提前确认核心结论成立，并把关键数字定下来写进报告首页 |

其中**检查 8 的口径对账**最值得说：我把 `item_amount + freight_amount - order_amount` 的差值单独列出来，它必须严格等于 `0.00`。这就是"能被 Excel 复算"那条验收标准的落地。

**研究生和工程思维的分水岭就在这里**：论文里不需要写"我怎么证明数据没搬错"，但企业里这是交付前的必经一步。

## 十、可迁移的方法论（换任何数据集都能用）

把上面所有东西抽掉具体内容，剩下这六步：

```
1. 体检     → 产出「数据坑清单」（尤其找"看着像但不是"的字段）
2. 定口径   → 产出「指标字典」，写进代码注释和报告首页
3. 分层     → 每层只解决一类问题，用四个判断问题决定表的归属
4. 清洗     → 类型/去重/兜底/派生在 SQL；异常只标记不删除；推断留给 Python
5. 汇总     → JOIN 前先对齐粒度
6. 校验     → 完整性 + 口径对账 + 坑位复查 + 基准冻结
```

**这套流程换成银行流水、用户行为日志、医疗数据，一样能用。** 这是 S1 真正想让你带走的东西——不是那几十条 SQL，是这套顺序。
